## High

### H1. Next.js 16.2.6 is inside the range of 9 published high-severity advisories
`npm audit --package-lock-only` reports **8 high-severity vulnerabilities** in the dependency tree. The most serious is in Next itself:

- **GHSA-6gpp-xcg3-4w24 — Middleware/Proxy bypass in App Router apps using Turbopack** affects `next 9.3.4-canary.0 – 16.3.0-preview.10`; this project pins `next 16.2.6` (`package.json:18`) and relies on `proxy.ts` as its auth gate. Mitigating factor: the bypass alone leaks nothing, because every route handler and page re-checks auth server-side (see Critical). But the gate is what turns unauthenticated hits into cheap 401/redirects, and the other Next advisories (Server-Action DoS, SSRF in Server Actions, cache confusion of response bodies, image-optimization DoS via SVGs, unauthenticated disclosure of internal Server Function endpoints) have no such second layer.
- Transitive highs: `brace-expansion` (3 DoS advisories), `js-yaml` (quadratic CPU), `nanoid` (infinite loop), `undici` (8 advisories incl. cross-user cache disclosure — reachable through Next's server fetch), `vite` (dev-only `server.fs.deny` bypass on Windows).
- Fix: all are flagged `fix available via npm audit fix`. Bump `next` past the 16.3.0 line first and re-run the suite.

### H2. Optimistic rating writes with no failure path
- `components/MediaCard.tsx:49-56` — `handleRatingChange` sets local star state, fires `PATCH /api/watch`, and ignores the result entirely: no `.ok` check, no try/catch, no rollback. A network failure or 401 leaves the card showing a rating the database never received, silently, until the next full refetch.
- `components/ShowDetailClient.tsx:103-111` — identical pattern (`setRating(newRating)` then an unchecked `fetch`).

Every other mutation goes through `lib/useMediaActions.ts` (typed errors callers handle) or has explicit catch/toast handling. These two bypass that convention. Small fix: check `res.ok`, revert on failure, toast.

## Medium

### M1. Real API key sitting in `.env.local` on disk
`.env.local:2-3` contains a live-looking `GEMINI_API_KEY="AQ.Ab8RN6..."` plus a Vercel OIDC token (its `exp` dates to June 2026 — expired, but still sensitive-shaped). This app uses neither variable (no `GEMINI_API_KEY` reference anywhere in `lib/` or `app/`); they arrived via `vercel env pull` ("Created by Vercel CLI", line 1). The file is properly gitignored (`.gitignore:34,47`) and was never committed (verified against full history). Still: an unused third-party credential in plaintext inside a repo directory that multiple agents and tools read is avoidable blast radius — remove the lines and rotate the key if it's used elsewhere.

### M2. Library's initial-fetch failure renders as "nothing logged yet"
`components/LibraryView.tsx:187-189` — the mount effect swallows fetch errors with an empty catch (the comment says this avoids unhandled rejection). Consequence: if `/api/watch` fails on first load, `loading` flips false, `entries` stays `[]`, and the user sees the EmptyState "No titles logged yet" (`LibraryView.tsx:554-561`) — a lie about their data. The manual-refresh path does toast (`:232-235`); the mount path should too, or show a retry state.

### M3. `season_id` skips UUID validation on the episodes endpoints
`app/api/episodes/route.ts:14` accepts any non-empty string for `season_id`, while sibling routes validate with `parseUuid` (`app/api/watch/route.ts:114,157`). A malformed id flows into `.eq('season_id', …)` and surfaces as a PostgREST cast error → **500** instead of a clean 400. Same for DELETE (`:81-99`). Low exploit value (RLS scopes everything to the caller) — purely correctness/consistency, but it is the one gap in an otherwise uniform validation layer.

### M4. Watchlist PATCH validates `id` less strictly than its siblings
`app/api/watchlist/route.ts:204` checks only `typeof id !== 'string'`; the watch routes use `parseUuid` (`lib/validation.ts:100-110`). A non-UUID string 500s at the database instead of 400ing at the door.

### M5. `/api/person` bypasses the shared TMDB plumbing — including its timeouts
`app/api/person/route.ts:35,48` hand-roll `fetch()` against TMDB instead of using `fetchTmdb`/`apiUrl` from `lib/tmdb.ts`, and miss the 8-second `AbortSignal.timeout` every other TMDB call gets (`lib/tmdb.ts:130-141`). A slow TMDB response hangs this route until the platform timeout. The response mapping (`mapItem`, `:69-84`) is also a near-duplicate of the mappers in `lib/tmdb.ts:389-402`.

### M6. Import-by-title can attach the wrong title silently
`app/api/import/route.ts:51-64` searches TMDB with the raw title and falls back to `results[0]` when neither type nor year narrows the list. A vague title imports whichever result TMDB ranks first — logged as *watched*, with the user's rating attached. The skip-if-existing check (`:69-77`) keys on the matched media, so re-importing won't surface the mistake either. Acceptable for a personal tool; worth knowing.

### M7. Signup throttle: unbounded per-instance Map, IP-keyed
`app/api/auth/signup/route.ts:20-32` — `attempts` is a module-level `Map` keyed by spoofable `x-forwarded-for` (`:63-65`) with no eviction beyond per-key reset. An attacker cycling fake XFF values grows the map without bound on a long-lived instance. The code itself calls it "a speed bump rather than a lock" (`:16-19`) — fine single-user; don't expose signup publicly without moving this to shared storage.

## What's actually good

This is an unusually disciplined codebase. Highlights worth preserving as conventions:

- Validation layer: every mutating route funnels through `lib/validation.ts` — bounded text, real-calendar-date checking (`parseDate` rejects `2026-02-30`, :73-80), 0.5-step ratings, UUID regex, and a safe `readJson` returning 400 on malformed bodies (just landed in HEAD commit 24a5436).
- Crypto hygiene: invite code and admin bearer comparisons hash-then-timingSafeEqual (`lib/auth.ts:15-20`, `app/api/admin/backfill-collections/route.ts:8-14`). Open-redirect guard on emailed `next` params covers both `//evil.com` and backslash variants (`lib/auth.ts:31-37`).
- Database: migration 011 replaces a check-then-insert TOCTOU with a partial unique index (`supabase/migrations/011_perf_and_security_audit.sql:13-16`); share tokens are read exclusively through token-gated SECURITY DEFINER RPCs with RLS fully locked (`006_share_rpcs.sql`, hardened in `011:153-208`, private review column stripped from shared output); `(tmdb_id,type)` uniqueness fixed the movie/show ID collision (`009_media_tmdb_type_unique.sql`).
- Correctness infrastructure: `lib/fetchAllRows.ts` walks PostgREST's silent 1000-row cap with deterministic tiebreak ordering; `lib/pool.ts` caps bulk-action concurrency; LibraryView guards every async settle with generation counters (`components/LibraryView.tsx:174-205`) so stale responses cannot win.
- Performance posture: DB-side grouping RPC for Continue Watching (`010_continue_watching.sql`), batched client rating lookups (`lib/tmdbRatings.ts`), tiered TMDB revalidate windows (`lib/tmdb.ts:12-16`), deferred charts. No N+1s found: list queries embed media via PostgREST joins, and the one per-card lookup that existed was batched server + client side.
- CSV export escapes formula injection (`app/api/export/route.ts:5-13`).
- Tests: ~50 spec files across lib/__tests__, components/__tests__, app/__tests__ covering the pure domain logic (stats, validation, TMDB mapping, filters) and most hooks; vitest.config.ts:11-17 documents and fixes a real cross-file mock-leak flake. ## Architecture overview

Next.js 16 App Router, React 19, Tailwind v4, Supabase (Postgres + Auth), TMDB as metadata source. Deployed on Vercel.

- Routing: `app/(app)/` holds authenticated pages (dashboard, library, watchlist, shows, collections, calendar, stats, streaming, recommendations, settings, import); `app/(public)/` holds login/signup/password plus token-guarded share pages. Legacy routes live on as redirects (`lists/page.tsx`, `movies/page.tsx`) — intentional and documented.
- Auth: proxy.ts (Next 16's middleware) verifies the JWT locally via getClaims() against a cached JWKS, redirects pages / 401s APIs, shares cookie-rotation logic with `lib/supabase/server.ts`. Every server component and route handler independently re-checks via the react.cache-wrapped `getAuthenticatedUser()`.
- Data flow: server components fetch through the Supabase SSR client and stream initial props into client islands (LibraryView, ShowDetailClient, WatchlistContent). Client mutations go through REST handlers under app/api/*; the browser no longer talks to PostgREST directly (`app/api/library/ids/route.ts:21-22`).
- Shared cache model: media/seasons/episodes are global TMDB-derived caches readable by all; per-user state (watch_entries, watchlist_items, episode_progress, followed_shows, user_settings) is RLS-scoped. Sharing rotates UUID tokens checked inside SECURITY DEFINER RPCs.

Nothing structurally confusing found beyond the duplications in L3/M5; module boundaries (pure logic in lib/, IO in routes, presentation in components/) are consistently respected.
