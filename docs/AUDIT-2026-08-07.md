# DorfMovies — Full Feature Audit (2026-08-07)

Supersedes `docs/AUDIT.md` (2026-06-06). Stack: Next.js 16.2.6 (App Router, `proxy.ts`), React 19.2.4,
Supabase (`@supabase/ssr`, anon key only), TMDB, Tailwind v4, Vitest, Recharts, Framer Motion.
~10,000 lines across 47 source files, 30 components, 21 API routes, 6 migrations.

> **Note on verification:** `node_modules` is not installed in this environment, so `vitest` and
> `eslint` could not be run. Every finding below comes from reading source, not from a test failure.
> Line references are to the code as of commit `557b705`.

## 2. Bugs & things that could update existing features

Ranked by user-visible impact.

### B1. Episode tracking is unreachable — the feature is stranded 🔴

`/show/[id]` is the only place `EpisodeTracker` renders, and the **only link to it in the entire
codebase** is `ContinueWatchingRow.tsx:143`. That row only renders when `episode_progress` rows
already exist (`app/page.tsx:194`). So:

- To track episodes you must already have episode progress.
- The only thing that creates initial progress is CSV import, which marks **every episode of every
  season watched** (`app/api/import/route.ts:58-72`).
- Nothing in Search → modal, Movies/Shows → `MediaCard` → modal, or the Sidebar links to `/show/[id]`.

You have a working episode tracker (97 lines), a detail page (111 lines), an API (`/api/episodes`),
a `seasons` table and an `episode_progress` table — and no way in. **Fix:** add a "Track episodes"
button to `MediaInfoModal` for `type === 'show'` that resolves the local `media.id` and links to
`/show/[id]`. This is the single highest-value change in this document: it unlocks a whole feature
you already paid for.

### B2. `/api/watch?type=` doesn't filter — every library page downloads your whole history 🔴

`app/api/watch/route.ts:16-22` selects `'*, media(*)'` then applies `.eq('media.type', type)`.
In PostgREST, filtering an embedded resource **without `!inner`** filters the embedded rows, not the
parent rows — so you get *every* watch entry back, with `media: null` on the ones that don't match.

That's why both library pages carry a client-side workaround
(`app/movies/page.tsx:31-33`, `app/shows/page.tsx:31-33`) discarding what the server should never
have sent. With 500 logged titles, `/movies` transfers all 500 with full media payloads to render
maybe 300. `/api/watchlist` gets this right (`media!inner(*)`, line 21) — `/api/watch` is simply
inconsistent.

**Fix:** `select('*, media!inner(*)')` in `/api/watch`, then delete both client-side filters.

### B3. Hardcoded `localhost:3003` link shipped to production 🔴

`components/MediaInfoModal.tsx:304-314` renders a "Watch on IPTV" button for **every movie**, pointing
at `http://localhost:3003/?q=...`. For anyone who isn't you on your dev machine this is a dead link
in the primary UI surface. Move the base URL to an env var and hide the button when it's unset.

### B4. `SelectableOverlay` calls a hook conditionally — latent crash 🔴

```tsx
// components/SelectableOverlay.tsx:9-10
if (!item) return <>{children}</>          // early return…
const { selectedItems, ... } = useMultiSelect()   // …before a hook
```

`app/watchlist/page.tsx:314` passes `selectableItem as TmdbSearchResult`, and `selectableItem` is
`null` whenever `item.media` is falsy (line 303-311). A single watchlist row with a missing media join
changes the hook count between renders → *"Rendered fewer hooks than expected"* and the page dies.
The `as` cast is what hides this from the type checker. **Fix:** move the guard below the hook call,
and drop the cast so the real `null` shows up in the types.

### B5. `/api/tmdb/rating` fetches a full detail payload to return one number 🟡

`MediaCard.tsx:26-35` fires this per card when `vote_average` is null. The route
(`app/api/tmdb/rating/route.ts:13`) calls `fetchTmdbDetails`, which requests
`append_to_response=credits,videos,watch/providers,external_ids` (`lib/tmdb.ts:137`) — full credits,
all trailers, every provider — and then returns `{ vote_average }`. On a 40-card library page with
un-backfilled rows that's 40 of the heaviest TMDB calls available.

Three compounding fixes: backfill `media.vote_average` (migration 004 added the column, `upsertMedia`
now populates it — old rows are still null), drop the `useEffect`, and give `fetchTmdbDetails` an
`append` parameter so cheap callers can opt out.

### B6. Zero TMDB caching, and it's costing more than in June 🟡

Still no `revalidate`, `'use cache'`, or `cacheLife` anywhere. In Next 16 `fetch` defaults to
no-store, so every one of these is a live call:

| Path | TMDB calls per request |
|---|---|
| `getPopularCollections` (`lib/tmdb.ts:344`) | **21** — 1 popular + 20 detail fetches, because `belongs_to_collection` isn't in list responses |
| `/api/calendar` | **5 + up to 25** — 3 movie pages, 2 show pages, then one `/tv/{id}` per followed show |
| `/api/recommendations` | **15** parallel recommendation calls (or **5** trending on the cold path) |
| `/api/versus` | **6** discover pages |
| `/api/tmdb/rating` | 1 heavyweight call **per card** |

TMDB metadata barely changes. `cacheLife('days')` + a `cacheTag` per `tmdb_id` on the `lib/tmdb.ts`
reads is a small diff with a large effect on latency, cost, and rate-limit headroom.

### B7. Marking a season watched fires one request per episode 🟡

`EpisodeTracker.tsx:21-39` loops and calls `onProgressChange` per episode without awaiting; the show
page turns each into its own `POST /api/episodes` (`app/show/[id]/page.tsx:56-75`). Clicking E24 of a
24-episode season fires 24 parallel writes, each doing its own auth round-trip. Accept an array (or a
`{from, to}` range) in `/api/episodes` and send one request.

### B8. `proxy.ts` fails open, and 5 routes have no auth of their own 🟡

`proxy.ts:48-50` swallows every exception and returns `NextResponse.next()`. If Supabase is briefly
unreachable, the auth gate opens. Most routes re-check auth themselves and stay safe — but these
don't:

- `/api/tmdb/rating`, `/api/person`, `/api/streaming`, `/api/tmdb/popular-collections` — no auth at all
- `/api/calendar` — reads the user opportunistically but never gates on it

During a Supabase blip these become an open proxy to TMDB on your API key. Add the same
`getUser()`/401 guard the other 16 routes use.

### B9. `error.tsx` still leaks messages and can't recover 🟡

`app/error.tsx:8-10` renders `{error.message}` in a `<pre>` and offers no `reset()`. Unchanged since
June. Generic copy + a "Try again" button is a 10-line fix.

### B10. Client reads pull unbounded tables to build ID sets 🟡

`search/page.tsx:24-27`, `streaming/page.tsx:48-51` and `SimilarModal.tsx:36-39` each run the same
pair of queries selecting **every** watch entry and watchlist item to build two `Set`s of `tmdb_id`.
`SimilarModal` re-runs it every time the modal opens. Fine at 50 titles, not at 2,000. Worth an
endpoint returning just the ID arrays, cached per session (see S4).

### B11. Missing indexes on the hottest columns 🟡

`005_watchlist_indexes.sql` indexed `watchlist_items(user_id)`, `media(type)` and `media(genres)`.
Nothing indexes:

- `watch_entries(user_id)` — read by the dashboard, stats, library, recommendations, versus, export
- `watch_entries(media_id)`, `watch_entries(watched_at)`
- `episode_progress(user_id)`, `episode_progress(season_id)`
- `followed_shows(user_id)`, `list_items(list_id)`

`watch_entries` is the most-read table in the app and has no index on the column every query filters.

### B12. No defence in depth on read paths (June's C2, still open) 🟡

`app/page.tsx:59-61`, `app/stats/page.tsx:8-9`, `app/api/export/route.ts:17-18` and
`app/lists/page.tsx:17` query user-scoped tables with **no `.eq('user_id', …)`**, trusting RLS alone.
It works today. It means one bad migration turns the app into a public data dump. `collections/[id]`
already does it correctly (lines 40-41) — make it uniform.

### B13. Smaller items

- **`upsertMedia` re-fetches TMDB on every write** (`lib/media.ts:10`) — marking an already-cached
  title watched still costs a full detail call, then does a second `UPDATE` for
  `collection_id`/`vote_average` that the first upsert could have carried (lines 43-49).
- **`.single()` where no row is legal** — `app/show/[id]/page.tsx:39`, `app/settings/page.tsx:14`,
  `app/api/follow/route.ts:14,17,48`. Returns a PGRST116 error instead of `null`; use `maybeSingle()`.
- **`/api/admin/backfill-collections` is still a silent no-op** (June's C4) — a sessionless anon
  client can't satisfy `media`'s `auth.uid() is not null` update policy, so it reports `updated: N`
  from TMDB data while writing zero rows. `ADMIN_SECRET` is still absent from `.env.local.example`.
- **`next.config.ts` is still empty** — no security headers, no `images.remotePatterns`.
- **No `loading.tsx` anywhere** — server pages block on `Promise.all` behind a blank screen.
- **Genre lists disagree.** `lib/tmdb.ts:19-47` collapses Action/Adventure/Sci-Fi into
  `'Action & Sci-Fi'`, but the watchlist filter dropdown (`app/watchlist/page.tsx:24-29`) lists raw
  TMDB names like `"Action"`, `"Science Fiction"`, `"Sci-Fi & Fantasy"`. Those options match nothing
  for anything added via search — while `upsertMedia` stores TMDB's *real* names from the detail
  endpoint. Two genre vocabularies in one database. Pick one and normalise on write.
- **Dead conditional** — `app/watchlist/page.tsx:260-263`: the outer `if` and inner `if` can only both
  hold when `priority !== 'must_watch'`, so the whole block reduces to "hide empty non-must-watch
  sections when unfiltered."
- **`app/api/versus/route.ts:9-12` re-implements `apiUrl`** already in `lib/tmdb.ts:72`.

## 3. Simplification — fewer components, less code

30 components today. The duplication is concentrated in four places, and collapsing them removes
roughly **1,000 lines** while *reducing* component count to ~22.

### S1. `/movies` and `/shows` are the same file twice → **-145 lines, -1 page**

`app/movies/page.tsx` and `app/shows/page.tsx` are 145 lines each and differ only in: the fetch
query string, the `<h1>`, two placeholder strings, and two empty-state sentences. Everything else —
state, sort options, the sort-pill markup, the skeleton grid, the refresh handler — is byte-identical.

Extract `components/LibraryView.tsx` taking `{ type, title, noun }`; both pages become 6-line
wrappers. Combined with B2 the client-side type filter disappears too.

### S2. Thirteen copies of the same two handlers → **-180 lines**

`onAddToWatchlist` / `onMarkAsWatched` are written inline as raw `fetch` calls in **13 files**:
`person`, `streaming`, `versus`, `watchlist`, `search`, `recommendations`, `calendar`,
`CollectionMovieCard`, `MediaCard`, `DashboardRecentCards`, `SimilarModal`, `DashboardSearchBar`,
`DashboardUpcomingWidget`. Every one repeats the same headers object and the same
`new Date().toISOString().split('T')[0]`.

They also disagree in ways that look accidental rather than intentional: `recommendations`, `person`
and `calendar` add at `must_watch`, everywhere else uses `want_to_watch`. Some call `router.refresh()`,
some update local state, some do neither.

Extract one hook:

```ts
// lib/useMediaActions.ts
export function useMediaActions(opts?: { priority?: WatchlistPriority; onDone?: () => void })
// → { addToWatchlist, markWatched, removeFromWatchlist }
```

### S3. Four components wrap a tile in the same two things → **-3 components, ~-170 lines**

`MediaCard` (139), `CollectionMovieCard` (82), `DashboardRecentCards` (72) and the inline card in
`app/watchlist/page.tsx` all do exactly: build a `TmdbSearchResult`, wrap in `SelectableOverlay`,
render a tile, portal a `MediaInfoModal` with the two S2 handlers. Only the tile differs
(`MediaRow` vs `PosterCard` vs bespoke).

Collapse to one `components/MediaTile.tsx` with `variant="row" | "poster" | "compact"`, taking a
`TmdbSearchResult` plus optional `entry` for rating/review/actions.

### S4. The `Media → TmdbSearchResult` mapping is written 6 times → **-60 lines**

June flagged this as A2 with two sites. It's now six: `MediaCard.tsx:37-46`,
`DashboardRecentCards.tsx:17-28`, `CollectionMovieCard.tsx:21-28`, and `app/watchlist/page.tsx` at
**229, 250 and 304** — three times in one file. One `lib/mediaToResult.ts` export.

Same story for the watched/watchlist ID-set fetch (B10), duplicated verbatim in three files →
one `useLibraryIds()` hook.

### S5. `/api/calendar` duplicates `fetchUpcomingReleases` → **-136 lines, -1 route**

`app/api/calendar/route.ts` (136 lines) and `lib/tmdb.ts:377-466` (`fetchUpcomingReleases`, 90 lines)
implement the same feature against the same endpoints with the same mapping, dedup and sort. The
dashboard calls the lib function; `/calendar` calls the route. They've already drifted — the route
fetches 3 movie + 2 show pages, the lib function fetches 1 + 1, and only the route resolves followed
shows' next episodes.

Keep one implementation in `lib/tmdb.ts` with a `pages` option and a `followedShows` argument; delete
the route and have `/calendar` be a server component, which also removes a client round-trip.

### S6. Lower-value tidying

- `components/ui/Eyebrow.tsx` (25) and `BentoGrid.tsx` (42) are used only by `app/page.tsx`. Fine to
  keep, but they're one-consumer abstractions.
- Inline `style={{…}}` objects and Tailwind classes are mixed throughout, sometimes in one element
  (`app/movies/page.tsx:104` uses a `style` grid inside a Tailwind tree). Not a bug — but it's why
  the sort-pill markup got copy-pasted instead of extracted.
- The sort-pill button markup is repeated verbatim in `movies`, `shows` and `streaming`. One
  `<FilterPills>` covers all three.

**Net effect of S1–S5:** 30 components → ~22, ~1,000 lines removed, and the `must_watch` vs
`want_to_watch` inconsistency resolves itself as a side effect.

## 4. New feature ideas (not already present)

Ordered by leverage. The first five need **no new schema** — the data is already in your database
and unused.

### Cheap, because the data already exists

1. **Rewatch logging.** `watch_entries.rewatch` has existed since `001_initial.sql` and *nothing in
   the UI ever sets it*. `/api/watch` accepts it (line 35) and uses it to skip the duplicate check
   (line 40). Add a "Log a rewatch" action in `MediaInfoModal` and a rewatch count on cards — a
   genuinely popular tracker feature, already three-quarters built.

2. **Episode progress on show cards.** `episode_progress` + `seasons` give you exact counts. Show
   "14/24 · 58%" with a progress bar on show cards instead of a binary watched flag. `getEpisodeStats`
   in `ContinueWatchingRow.tsx:53-66` already computes it — it's just not used anywhere else.

3. **"What can I watch in 90 minutes?"** `media.runtime_mins` is stored and used only for the stats
   "Hours" tile. A runtime slider on the watchlist ("under 100 min") is a filter over data you have.

4. **Collection completion.** `collection_id`/`collection_name` are stored, and `/collections/[id]`
   already knows which parts you've seen. Surface "5/8 watched" per franchise and a "3 left in this
   collection" nudge.

5. **Diary / timeline view.** `watched_at` is a real date on every entry, and nothing presents the log
   chronologically — `/movies` and `/shows` are type-split grids. A reverse-chronological diary
   grouped by month is the view most trackers lead with, and it's a query you already run.

### Medium effort, high value

6. **"Not interested" list.** Recommendations exclude watched and watchlisted items
   (`/api/recommendations:111`) but there's no way to dismiss a suggestion permanently, so the same
   titles keep resurfacing across refreshes. One `dismissed_media` table + one exclusion.

7. **"On my services right now."** You already fetch `watch_providers` per title
   (`lib/tmdb.ts:144-150`) and know the 7 providers from `/streaming`. Let users pick their
   subscriptions in Settings, then filter the watchlist to what's streamable tonight. This is the
   feature that turns the watchlist from a list into a decision.

8. **Year in review.** `computeGenreBreakdown`, `computeMonthlyActivity`, `computeTopDirectors` and
   `computeTopActors` all exist in `lib/stats.ts`. A shareable year-end page is mostly presentation
   over functions you've already written and tested — and it plugs into the share-token
   infrastructure from `006_share_rpcs.sql`.

9. **Followed-show notifications.** `followed_shows` exists and `/calendar` already resolves each
   show's `next_episode_to_air`. Nothing notifies anyone. A weekly digest (or web push) is the payoff
   for the follow button that currently only decorates the calendar.

10. **Command palette (⌘K).** 12 nav destinations behind a "More" drawer, plus search as its own
    route. One palette for search + navigate + "mark watched" collapses a lot of clicking.

### Larger bets

11. **Trakt / Letterboxd import.** CSV import exists but only for your own template
    (`ImportExportPanel.tsx:62`). Accepting Letterboxd's `diary.csv` and Trakt's export is the
    difference between an empty app and a full one on day one. Note the current importer posts rows
    **strictly sequentially** (`runImport`, line 102), each doing a TMDB search plus a detail
    fetch — a 500-row Letterboxd history would take many minutes. Batch it before advertising it.

12. **Friends / following.** Sharing today is one-way, token-per-link, read-only. Mutual follows with
    a comparison view ("you both rated this 5★", "3 films they loved that you haven't seen") is the
    natural extension, and recommendations get much better signal.

13. **PWA + offline.** Poster-heavy, read-mostly, mobile-first — a good fit. Depends on B6 caching
    landing first.

### Corrections to this document, found while implementing it

- **B6 — `'use cache'`/`cacheLife` were the wrong tool.** In Next 16 they require the
  `cacheComponents` flag, which forces Suspense boundaries around every dynamic read. Used
  per-request `fetch` revalidate windows instead: same win, no migration.
- **B5 — do not drop `MediaCard`'s `useEffect` yet.** It's only safe after backfilling
  `media.vote_average` for pre-migration-004 rows. Until then it's the sole source of a rating
  on old entries. `upsertMedia`'s cached path is also guarded on a non-null `vote_average` so
  those rows still refresh.
- **S4 — five mapping sites, not six.** The third watchlist line cited (229) is a fetch body.
- **S3 — rejected.** `mediaToResult` and `useMediaActions` already removed the shared parts.
  What's left diverges in every dimension, and critically the four sites use *three* different
  modal strategies: `MediaCard`/`CollectionMovieCard` portal per card, `DashboardRecentCards`
  renders one modal outside the loop, and the watchlist hoists it to the page across all three
  priority buckets. A per-card `MediaTile` would force the latter two to regress, in exchange
  for a four-branch component behind a wide prop union.
- **B13 genre vocabulary — false positive.** `TMDB_GENRES`' collapsed names
  (`'Action & Sci-Fi'`) are only used to render search/discover *list results* and are never
  persisted. The one write path takes genres from `fetchTmdbDetails`, which uses TMDB's real
  names — the same vocabulary the watchlist dropdown lists and the server filter matches.
- **Not in this document:** with `ADMIN_SECRET` unset, the backfill route compared against the
  literal string `"Bearer undefined"`, which anyone could send. Now 503s when unconfigured.

### Still open

- `media.vote_average` backfill for pre-migration-004 rows (unblocks deleting B5's `useEffect`).
- Apply migration `007_hot_path_indexes.sql`.
- `proxy.ts` still fails open (B8 hardened the routes, not the proxy).
- The `must_watch` vs `want_to_watch` split is preserved, not resolved — a product decision.
- S6 tidying (`<FilterPills>`, one-consumer `ui/` components) untouched.

**B1 first.** Everything else here makes the app faster, smaller, or safer; B1 is the one that makes
it do something it currently can't.
