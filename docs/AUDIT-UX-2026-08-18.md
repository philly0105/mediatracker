# DorfMovies — UX deep dive (2026-08-18)

Third audit in the series. The first two (`AUDIT.md`, `AUDIT-QOL-2026-08-07.md`)
were about bugs and missing infrastructure, and both are essentially closed —
toasts, undo, modals, keyboard shortcuts, URL-mirrored filters, TMDB caching,
`next/image`, RLS-safe sharing all landed. This one starts from the assumption
that the plumbing works and asks a different question: **what is it actually
like to use this app, every day, for the thing it exists to do?**

## Method and caveat

Every finding below was verified by reading the code at the cited line. Nothing
was exercised against a running app — there is no `.env.local` in this
checkout, so there are no Supabase or TMDB credentials here. Same caveat as
both previous rounds, and it still matters most for the layout/spacing items in
Tier 3.

Health of the tree as of this audit:

| Check | Result |
| --- | --- |
| `npx tsc --noEmit` | clean |
| `npm run test:run` | 261 passed / 33 files |
| `npm run build` | succeeds, 50 routes |
| `npm run lint` | **45 errors, 19 warnings** — see X1 |

## Tier 0 — things that are wrong right now

### U1. Undo silently does nothing for the last 2 seconds it is on screen

The single sharpest bug in the app, because it breaks the one affordance the
last audit added to make destructive actions safe.

- `useDeferredAction` commits the write after **6000 ms** ([useDeferredAction.ts:18](../lib/useDeferredAction.ts:18)).
- A toast carrying an action stays up for **8000 ms** ([ToastProvider.tsx:84](../components/ToastProvider.tsx:84)).

So for two full seconds, the Undo button is visible, hoverable, clickable — and
dead. Every call site guards with `if (!cancel(key)) return`, which returns
without a word:

- [LibraryView.tsx:129](../components/LibraryView.tsx:129) — deleted watch entry
- [watchlist/page.tsx:342](../app/watchlist/page.tsx:342) — removed watchlist item
- [show/[id]/page.tsx:198](../app/show/[id]/page.tsx:198) — un-marked episodes (this one can be *a whole season*)

The user clicks Undo, the toast dismisses (`handleAction` always calls
`dismiss`), and the row stays gone. It reads as "Undo is broken", not "you were
too late", which is worse.

**Fix, in order of preference:**

1. Make the toast duration derive from the deferral window rather than being an
   independent constant — pass `durationMs: 6000` at the three call sites, or
   better, export the delay from `useDeferredAction` and have the toast take it.
   Ideally the toast should disappear *slightly before* the commit (5500 ms), so
   there is no window at all.
2. Have `cancel()` returning false surface something: `toast('Too late to undo —
   that has already been removed.', { tone: 'info' })`.

Do both. (1) removes the window; (2) is the safety net for a slow click.

### U2. `/lists` is orphaned but fully alive

Commit `088344e` removed Lists from the sidebar and from the ⌘K quick-nav. It
did not remove anything else. A grep for links to `/lists` across `app/`,
`components/` and `lib/` returns **zero hits**, yet still shipping and reachable
by URL:

- `app/lists/page.tsx` — create and browse lists
- `app/lists/[id]/page.tsx` — list detail
- `app/api/lists/route.ts`, `app/api/lists/[id]/route.ts`, `app/api/lists/[id]/items/route.ts`
- `app/share/list/[token]/page.tsx` — public share page
- `supabase/migrations/003_collections.sql` tables + the `shared_list` RPC in `006_share_rpcs.sql`

The half-state is the problem. Anyone who bookmarked `/lists` gets a working
page with no way back into the app's navigation, can still create lists, and can
still generate share links — but Settings' sharing panel only offers Watched
History and Watchlist ([settings/page.tsx:61-72](../app/settings/page.tsx:61)),
so a list's share state is now only togglable from a page nothing links to.

**Decide, then commit to it.** Either put Lists back in `MORE_NAV`
([Sidebar.tsx:43](../components/Sidebar.tsx:43)) and `QUICK_NAV`
([SearchOverlay.tsx:21](../components/SearchOverlay.tsx:21)), or delete the
routes, the API, the share page, and add a redirect stub at `/lists` the way
`/search` and `/import` already do it. Leaving it as-is is the only bad option.

### U3. Recommendations "Refresh" does not fetch anything new

`loadRecommendations(true)` hits `/api/recommendations?refresh=1`
([recommendations/page.tsx:67](../app/recommendations/page.tsx:67)). Server-side,
`refresh` does exactly one thing: swap `sort by score` for
`shuffleWithinScoreBands` ([api/recommendations/route.ts:35-46](../app/api/recommendations/route.ts:35)).

The seeds are unchanged (same 15 rows), and the TMDB recommendation lists behind
them are cached for a day (`CACHE_1D`, [tmdb.ts:15](../lib/tmdb.ts:15)). So
"Refresh" reorders the same ~100 titles within their score bands and calls it
new. It also throws away the user's genre pill, type pill, and scroll position
([recommendations/page.tsx:74-79](../app/recommendations/page.tsx:74)), so it
feels like a hard reset that returned you to the same place.

**Fix:** make refresh mean something — rotate the seed window (`.range(15, 29)`
on the next press), or mix in `discoverByGenre` from the user's top genres. If
you keep the shuffle, rename the button to "Shuffle" and stop resetting the
filters.

### U4. Recommendations fall back to global trending for anyone who doesn't rate 4+

Seeds come from `watch_entries` filtered to `.gte('rating', 4)`, limit 15
([api/recommendations/route.ts:100-106](../app/api/recommendations/route.ts:100)).
If that returns nothing, the route serves five pages of TMDB weekly trending and
sets `fallback: true`, which renders the copy:

> "We compiled this week's overall trending items to get you started!"

A user with 250 logged titles who rates generously-but-not-effusively (or who,
very plausibly, has simply never rated anything) sees the exact same page as a
brand-new account, told they need to get started. The app has the data; it just
refuses to use it.

**Fix:** cascade the seed query instead of falling off a cliff —
`rating >= 4` → `rating IS NOT NULL` ordered by rating → the 15 most recent
entries regardless of rating → *then* trending. Only the last case should say
"to get you started". This is ~15 lines in the route and turns the most
prominent "personalized" surface from decorative into real for a large class of
users.

### U5. The Library never shows when you watched anything

`LibraryView` renders every card with `hideWatchedDate={true}` — both the grid
([LibraryView.tsx:307](../components/LibraryView.tsx:307)) and the list
([LibraryView.tsx:319](../components/LibraryView.tsx:319)). `MediaCard` then
treats that flag as a two-way switch:

```tsx
watchedAt={!hideWatchedDate ? entry.watched_at : null}
tmdbRating={hideWatchedDate ? tmdbRating : null}
```
— [MediaCard.tsx:117-118](../components/MediaCard.tsx:117)

So on the one page in the app dedicated to your viewing history, the watch date
is structurally unrenderable, and the slot is occupied by TMDB's public score
instead. The default sort is **"Recently watched"**
([LibraryView.tsx:47](../components/LibraryView.tsx:47)) — you are sorting the
list by a column it will not show you.

**Fix:** stop making these mutually exclusive. `MediaRow` already has room for
both (the meta row at [MediaRow.tsx:86-97](../components/ui/MediaRow.tsx:86) and
the footer at [MediaRow.tsx:109-113](../components/ui/MediaRow.tsx:109)). Show the
watched date always; keep the TMDB score in the badge row. Format it while
you're there — see U20.

### U6. Every library page fires up to 24 parallel rating requests

`MediaCard` runs an effect on mount that fetches `/api/tmdb/rating` whenever
`media.vote_average` is null ([MediaCard.tsx:40-50](../components/MediaCard.tsx:40)).
The library renders 24 cards per page and adds 24 more on every scroll
([LibraryView.tsx:24](../components/LibraryView.tsx:24)), so a library of
un-backfilled rows produces a burst of two dozen concurrent requests per page.

This was flagged as A3 in the *first* audit. `vote_average` has had a column
since migration 004 and there is a working backfill endpoint at
`app/api/admin/backfill-vote-average/route.ts`. Run it until `remaining` is 0,
then delete the effect — it becomes dead code the moment the column is filled.
Two of the three pieces of this fix already exist.

### U7. Streaming's "Hide watched" filters the page you already paid for

`visibleResults` filters `results` client-side after they arrive
([streaming/page.tsx:118-121](../app/streaming/page.tsx:118)). TMDB pages are 20
items; if you've seen 18 of them you get 2 posters and a mostly empty screen,
and if you've seen all 20 you get:

> "No unwatched titles found on this page."

...which correctly describes the implementation and tells the user nothing
useful. For someone with a large library — the exact user this page is for —
Netflix's popular page is mostly already-watched, so the feature degrades
precisely where it should shine.

**Fix:** treat the filter as a fill target, not a post-filter. Keep advancing
pages in the loader until `visibleResults.length >= 20` or `page >= totalPages`.
The infinite-scroll machinery is already there; it just needs to be driven by
the *visible* count rather than the raw one.

## Tier 1 — friction in the loop you run a hundred times

The core loop is: summon search → find the thing → log it. Everything here makes
that loop longer than it needs to be.

### U8. Logging from ⌘K costs a modal and a network round trip

The overlay knows, for every row, whether you've watched it or listed it — it
renders those badges ([SearchOverlay.tsx:292-322](../components/SearchOverlay.tsx:292)),
and it already holds `markWatched` / `addToWatchlist`
([SearchOverlay.tsx:40-43](../components/SearchOverlay.tsx:40)). But the only
thing a row click does is `setSelected(r)`, which opens `MediaInfoModal`, which
blocks on `/api/tmdb/details` before it can show you the Mark-as-Watched button.

For the app's most-repeated action, that's: type, arrow, Enter, wait for
details, find the footer button, click, then Escape twice.

**Fix:** put a `✓` and a `+` chip on the right of each result row, visible on
hover/focus and on the active row. Every dependency is already in scope; this is
maybe 25 lines and it turns logging into a two-keystroke operation.

### U9. The ⌘K footer advertises three keys; there should be five

`↑↓ Navigate · ↵ Open · Esc Close` ([SearchOverlay.tsx:339-341](../components/SearchOverlay.tsx:339)).
Pair U8 with `⌘↵` = mark watched and `⇧↵` = add to watchlist in
`handleInputKeyDown` ([SearchOverlay.tsx:117](../components/SearchOverlay.tsx:117)),
and update the footer. The palette becomes a logging tool rather than a
navigation tool that happens to open modals.

### U10. The same search box behaves differently on two pages

- **Library** searches title, director, cast, genres and year, AND-ing terms
  ([matchesLibraryQuery.ts:11-32](../lib/matchesLibraryQuery.ts:11)) — so
  "fincher 2014" works.
- **Watchlist** searches `ilike('media.title', …)` and nothing else
  ([api/watchlist/route.ts:77-79](../app/api/watchlist/route.ts:77)).

Both are labelled with a magnifying glass and generic placeholder text. Two
inputs that look identical and behave differently is a worse failure than one
that's simply limited. Widen the watchlist query (`.or()` across
`media.title`, `media.director`, or move to a `tsvector` if you'd rather do it
properly in SQL).

### U11. Changing a watchlist priority from the card is silent

The hover cluster's three priority buttons call `handleUpdatePriority`
([watchlist/page.tsx:285-306](../app/watchlist/page.tsx:285)), which removes the
card from the current section and bumps a refresh signal for the target
section — with **no toast** on success. Meanwhile the *same* action taken from
inside `MediaInfoModal` does toast ("Moved X to Must Watch",
[MediaInfoModal.tsx:257](../components/MediaInfoModal.tsx:257)).

So from the card, an item silently vanishes from where you were looking with no
statement of where it went — and because the sections are far apart vertically,
it often lands off-screen. Add the toast; consider making it carry an Undo, since
the reverse operation is trivially available.

### U12. You cannot un-rate something

`RatingStars` offers half-star and full-star hit zones and nothing else
([RatingStars.tsx:36-51](../components/RatingStars.tsx:36)). There is no way to
get back to "unrated" once you've touched it — but `parseRating` explicitly
accepts null ([validation.ts:19-22](../lib/validation.ts:19)) and PATCH passes
it straight through, so the API has supported this all along.

This bites hardest because of the *other* thing about `RatingStars` — see U31,
the hit targets are 12 px wide. Misclicks are common and irreversible.

**Fix:** clicking the currently-selected value clears it, plus a small "Clear"
affordance in the modal and edit-entry contexts.

### U13. Your rating renders twice, side by side

`RatingStars` prints `{value}/5` itself ([RatingStars.tsx:57](../components/RatingStars.tsx:57)),
and `MediaInfoModal` prints `{userRating} / 5` immediately after it
([MediaInfoModal.tsx:484](../components/MediaInfoModal.tsx:484)). The modal reads
`★★★★☆ 4/5 4 / 5`. Delete one — the component's internal one, so the callers
control the treatment.

### U14. Calendar is nearly unreachable on mobile

`/calendar` appears in exactly two places: the ⌘K quick-nav
([SearchOverlay.tsx:29](../components/SearchOverlay.tsx:29)) and the dashboard
widget's "Full view" link ([DashboardUpcomingWidget.tsx:58](../components/DashboardUpcomingWidget.tsx:58)).
It is not in `PRIMARY_NAV`, not in `MORE_NAV`, and therefore not in the mobile
More drawer, which is built from those two lists plus Settings
([Sidebar.tsx:58-62](../components/Sidebar.tsx:58)).

On a phone there is no ⌘K. So a whole page — one that does real work, fetching
3 movie pages + 2 show pages plus followed-show details — is reachable on mobile
only by tapping a small text link inside one dashboard widget. Add it to
`MORE_NAV`; that fixes desktop sidebar and mobile drawer in one line.

### U15. The show page's Back button dead-ends on a deep link

`/show/[id]` uses a raw `router.back()`
([show/[id]/page.tsx:251](../app/show/[id]/page.tsx:251)). You already
solved this — `BackButton` checks `window.history.length > 2` and falls back to a
route ([BackButton.tsx:10-14](../components/BackButton.tsx:10)) — and use it on the
collection detail page. Show pages are the ones people actually deep-link into
(from Continue Watching, from a shared link, from a bookmark), so this is the
page that most needs the fallback. Swap it in with `fallback="/library"`.

### U16. `/settings` blanks out while it loads

It's an async server component that awaits `auth.getUser()` and a
`user_settings` read ([settings/page.tsx:12-18](../app/settings/page.tsx:12))
with no `loading.tsx`. Only six routes have one: `/`, `/calendar`,
`/collections`, `/collections/[id]`, `/person/[name]`, `/stats`. The other
server-rendered routes either self-skeleton on the client or, like Settings,
show nothing at all.

A dozen-line skeleton matching the two-column card layout closes it.

### U17. The Library has a manual Refresh button

There's a Refresh control sitting in the filter bar
([LibraryView.tsx:272-285](../components/LibraryView.tsx:272)). It exists because
the list is client-fetched once in an effect and `router.refresh()` can't reach
it — a real constraint, honestly documented in the code. But from the user's
side, a "Refresh" button in a filter row is an admission that the page might be
lying to you, and it invites a click every visit.

**Fix:** refetch on window focus (`visibilitychange`), and keep the button but
demote it — or drop it once focus-refetch lands. The mutation paths already
patch local state correctly.

### U18. The Library ships your entire history in one payload

`fetchEntries` calls `/api/watch` with no pagination
([LibraryView.tsx:76-86](../components/LibraryView.tsx:76)), and the route selects
`overview`, `cast_members`, `director`, `genres` for every row
([api/watch/route.ts:6-7](../app/api/watch/route.ts:6)). At ~260 entries that's
fine; the concerning part is that `overview` and `cast_members` are in the wire
format purely so the client-side search can match against them, and neither is
ever rendered in the list.

This was P3 last round and it's still the kind of fine that stops being fine
without warning. The cheap half-measure: drop `overview` from the select (search
doesn't use it — [matchesLibraryQuery.ts:21-27](../lib/matchesLibraryQuery.ts:21)
reads title/director/year/cast/genres). The real fix is moving filtering to the
API and paginating, which is a bigger change and probably not worth it yet.

## Tier 2 — accessibility and input

These are cheap and they're the kind of thing that quietly excludes people.

### U19. Hover-only controls are invisible to keyboard users

Three action clusters are gated on `md:group-hover:opacity-100`:

- watchlist card priority + remove buttons ([watchlist/page.tsx:471](../app/watchlist/page.tsx:471))
- library poster-grid edit/delete ([MediaCard.tsx:86](../components/MediaCard.tsx:86))
- (mobile is fine — they're `opacity-100` below `md`)

Tabbing to them focuses an element at `opacity: 0`. The global
`:focus-visible` outline ([globals.css:136-139](../app/globals.css:136)) draws a
ring around nothing. Add `md:focus-within:opacity-100` to each container — three
class strings.

### U20. Raw ISO dates are shown to users in three places

- `PosterCard overlay={entry.watched_at}` on the dashboard renders
  `2026-08-14` in the hover chip ([DashboardRecentCards.tsx:36](../components/DashboardRecentCards.tsx:36))
- `MediaRow` renders `Watched {watchedAt}` verbatim ([MediaRow.tsx:111](../components/ui/MediaRow.tsx:111))
- the share pages inherit the same shapes

Meanwhile `EpisodeTracker` has a correct, locale-pinned, timezone-safe formatter
already exported: `formatAirDate` ([EpisodeTracker.tsx:23-30](../components/EpisodeTracker.tsx:23)).
Lift it to `lib/` and use it everywhere. Note the subtlety it already
handles — `new Date('2026-08-14')` parses as UTC and renders the previous day in
US timezones, which `DashboardUpcomingWidget.formatDate`
([DashboardUpcomingWidget.tsx:32-41](../components/DashboardUpcomingWidget.tsx:32))
does *not* handle. That widget is showing off-by-one dates today.

### U21. Star rating hit targets are 12 × 24 px

Each half-star is `w-1/2` of a `w-6` (24 px) container
([RatingStars.tsx:40-48](../components/RatingStars.tsx:40)) — so 12 px wide. WCAG
2.5.8 asks for 24 × 24 minimum; iOS guidance says 44. On a phone, "I meant 4,
I got 3.5" is the default outcome, and per U12 you can't undo it.

**Fix:** bump the star container to `w-8 h-8` (or add `py-2 -my-2` padding to the
hit zones so the visual size is unchanged but the target grows). Cheap, high
impact on mobile.

### U22. The ⌘K result list isn't announced to screen readers

The overlay is a proper dialog — `role="dialog"`, `aria-modal`, focus trap via
`useModal`, all good. But the results are plain `<button>`s in a scrolling div
([SearchOverlay.tsx:210-334](../components/SearchOverlay.tsx:210)), and the
arrow-key highlight is purely visual (`activeIndex` → a background class). A
screen reader user pressing ↓ hears nothing; the AT cursor never moves.

**Fix:** `role="listbox"` on the list container, `role="option"` +
`aria-selected` on rows, `aria-activedescendant` on the input pointing at the
active row's id. ~10 lines and it makes the palette usable non-visually.

### U23. Nav items don't announce which page you're on

`NavItem` styles the active state richly (colour, background, border, icon tint)
but never sets `aria-current` ([NavItem.tsx:15-33](../components/ui/NavItem.tsx:15)).
Same for the mobile bottom bar ([Sidebar.tsx:263-300](../components/Sidebar.tsx:263))
and the More drawer. One attribute: `aria-current={active ? 'page' : undefined}`.

### U24. The search-mode tabs are a tablist with no tabpanel

`role="tablist"` / `role="tab"` / `aria-selected` are set
([SearchOverlay.tsx:192-207](../components/SearchOverlay.tsx:192)) but the results
region has no `role="tabpanel"` and no `aria-labelledby` pointing back. Either
complete the pattern or drop the roles and use `aria-pressed` toggle buttons —
the latter is closer to what this actually is.

## Tier 3 — polish

### U25. Streaming is hardcoded to seven US services

`PROVIDERS` is a literal seven-entry array ([streaming/page.tsx:15-23](../app/streaming/page.tsx:15)),
and `watch_region: 'US'` / `region: 'US'` are baked into
[tmdb.ts:443](../lib/tmdb.ts:443) and [tmdb.ts:649](../lib/tmdb.ts:649). Fine for
a personal app; worth a line in Settings if it ever isn't. Flagging it so the
constraint is a decision rather than an accident.

### U26. `MediaInfoModal` refetches details every single time it opens

`/api/tmdb/details` runs on every mount ([MediaInfoModal.tsx:120-153](../components/MediaInfoModal.tsx:120)),
even for a title you opened thirty seconds ago. The route itself does a TMDB
call (cached server-side, so cheap) *plus* three-to-four Supabase reads
([api/tmdb/details/route.ts:27-59](../app/api/tmdb/details/route.ts:27)). This is
the most-opened surface in the app.

A module-level `Map<string, FullDetails>` keyed on `${type}-${tmdb_id}`, served
immediately and revalidated in the background, would make the modal feel instant
on the second open. ~20 lines, and it's the single biggest perceived-speed win
left.

### U27. The Ratings chart is labelled "Films" but counts shows too

`computeRatingDistribution(all)` is fed every watch entry including shows
([stats/page.tsx:66](../app/stats/page.tsx:66) → [stats.ts:22-31](../lib/stats.ts:22)),
but the bar's series name is `"Films"`
([StatsCharts.tsx:86](../components/StatsCharts.tsx:86)), which is what the
tooltip shows. Rename it to "Titles".

### U28. Stats is missing the numbers a tracker exists to produce

The page has Movies / Shows / Episodes / Hours, a genre pie, a rating histogram,
monthly activity, top directors and top actors. What it doesn't have, all of
which is computable from data already queried:

- **Your top-rated titles** — you have every rating; the app never shows you
  your own best-of list.
- **Rewatch count** — the `rewatch` column is selected in the stats query
  ([stats/page.tsx:32](../app/stats/page.tsx:32)) and then never used.
- **Current / longest streak** — `watched_at` is right there.
- **A year selector** — `computeMonthlyActivity(all, watchedEpisodes, 12)` is a
  hardcoded rolling 12 months; a `2025 / 2026 / All` toggle costs almost nothing
  and is the "wrapped"-style view people actually want.

All four are pure functions in `lib/stats.ts` next to an existing test file —
the cheapest feature work available in the repo.

### U29. Episode tracker uses text glyphs for its chevrons

`{isOpen ? '▲' : '▼'}` ([EpisodeTracker.tsx:120](../components/EpisodeTracker.tsx:120))
in an app that imports lucide everywhere else. `ChevronUp`/`ChevronDown`.

### U30. `Button` silently breaks if a caller passes a mouse handler

`onMouseEnter`/`onMouseLeave` are set before `{...rest}`
([Button.tsx:61-62](../components/ui/Button.tsx:61)), so any caller passing
either wins the spread and kills all hover styling on that button with no error.
Also worth noting: hover-as-`useState` re-renders the component on every pointer
enter/leave — with a dozen buttons on screen that's a lot of avoidable renders
for something CSS `:hover` does for free. Same pattern in `Input`, `PosterCard`,
`MediaRow`, `NavItem`.

Not urgent. But if you ever touch the design system, moving hover to CSS is the
change with the best ratio.

### U31. Empty-state copy is good; two states render at once on the dashboard

`DashboardRecentCards` renders its (empty) grid and *then* the `EmptyState`
renders below it ([page.tsx:208-219](../app/page.tsx:210)). Harmless today
because an empty grid has no height, but it's two components owning one state.
Move the check above the cards.

## Code health

### X1. `npm run lint` fails — 45 errors, 19 warnings

Lint is not a gate today, which means it can't catch anything. The breakdown:

| Category | Count | Notes |
| --- | --- | --- |
| `@typescript-eslint/no-explicit-any` | ~25 | Concentrated in the share pages, `/api/recommendations`, `/api/export`, `stats/page.tsx` |
| `react-hooks/set-state-in-effect` | 6 | `lists`, `recommendations`, `watchlist`, `MediaInfoModal`, `MultiSelectProvider`, `PopularCollectionsFeed` |
| `react-hooks/refs` | 2 | **[useTmdbSearch.ts:21,23](../lib/useTmdbSearch.ts:21)** — ref writes during render |
| unused imports/vars | ~12 | `Plus`/`Check`/`Loader2` in `person`, `Bookmark`/`Film`/`Tv` in `recommendations`, `Link`/`ArrowLeft` in `collections/[id]` |
| `no-img-element` | 3 | `MediaInfoModal` provider logos, `Sidebar` ×2 (dicebear avatars) |

The `useTmdbSearch` ref writes are the only ones with real teeth — they're in the
hook that powers ⌘K, and writing `modeRef.current = mode` during render is
exactly the pattern React 19's compiler-adjacent rules are warning about. The
fix is a `useEffect` (the file already has three).

**Recommended sequencing:** delete the unused imports (5 minutes), fix the two
ref writes, add `// eslint-disable-next-line` with a reason to the
`set-state-in-effect` cases that are genuinely intentional (several already have
comments explaining why — they just don't have the disable), type the `any`s at
the share/API boundaries, then make lint a CI gate so it stays clean.

### X2. `/show/[id]` queries Supabase directly from the browser

Every other data path in the app goes through `/api/*`; this page uses
`createClient()` from `lib/supabase/client` and issues four queries itself
([show/[id]/page.tsx:38-62](../app/show/[id]/page.tsx:38)). It works — RLS
scopes it — but it's the only place doing so, which means it's the only place
where a schema change won't be caught by the API layer's types. Flagged in the
last audit as P2 (the sequential-round-trip half was fixed; the architectural
half wasn't).

## Suggested order of work

**Half a day, highest impact:**

1. **U1** — align the undo window (it's a two-line constant change plus a toast)
