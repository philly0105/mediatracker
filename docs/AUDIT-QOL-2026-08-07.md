# Quality-of-life & feature audit — 2026-08-07

Companion to `AUDIT-2026-08-07.md`, which covered bugs and simplification. This
one covers everything that makes the app feel unfinished to use, plus features
the schema is already carrying but the UI never exposes.

Every item below was verified by reading the code, not inferred. Nothing here
has been exercised against a running app — same caveat as the last audit.

Prefix key: **Q** = quality of life, **F** = feature, **P** = polish/perf.

## Status

Done: **Q1–Q9, F1–F7, P1–P4** — every item in this document.

**F2 is now complete.** Migration 008 adds an `episodes` table (applied to the
live project), and the tracker renders `E4 · Fly · Mar 3, 2020` instead of `E4`,
dimming anything that has not aired yet. There is deliberately no backfill
script: episode names cost one TMDB request *per season*, so fetching them at
ingest would make marking a ten-season show watched wait on ten round trips.
`GET /api/episodes/meta` fills them the first time a show's page is opened
instead, which heals the existing library on its own. Specials are still out —
that decision is documented in `tmdb.ts` and unchanged.

**F6 is now done, as invite-gated signup.** `/signup`, `/forgot-password`,
`/reset-password` and an `/auth/callback` route that exchanges the emailed code
for a session. Signup requires a code held in `SIGNUP_INVITE_CODE`, checked
server-side only — it is not `NEXT_PUBLIC_`, so the form cannot validate it and
the browser never sees it. With the variable unset, signup is off entirely: the
route returns 503, the page says so, and the login screen hides the link.

**Three things this needs from you before it works:**

1. Set `SIGNUP_INVITE_CODE` in `.env.local` (and in your deploy's environment).
   Long and random — the throttle in the route is per-instance and only a speed
   bump.
2. In the Supabase dashboard, add `<your-url>/auth/callback` and
   `http://localhost:3000/auth/callback` to Authentication → URL Configuration →
   Redirect URLs. Emailed links land nowhere useful until you do.
3. Turn on leaked-password protection (Authentication → Policies). It is off,
   and it is the only security advisory on this project that isn't the share
   RPCs working as designed. It mattered less when nobody could sign up.

**One action needed from you**: `POST /api/admin/backfill-show-runtime` until
`remaining` is 0. 24 of your 26 shows have a null `runtime_mins`, so until that
runs, the Hours stat still excludes all TV — see Q5 below for why.

Nothing here has been exercised against a running app — there are no Supabase
or TMDB credentials in this environment, so all four are verified by tests and
by reading, not by clicking. See "What still needs a browser" at the bottom.

## Tier 1 — things that are actually wrong

### Q1. Deleting a card from /movies or /shows leaves it on screen

`MediaCard.handleDelete` succeeds, then calls `router.refresh()`
([MediaCard.tsx:64](../components/MediaCard.tsx:64)). But `LibraryView` is a
client component holding `entries` in `useState`, populated by a `fetch` to
`/api/watch` in a `useEffect` ([LibraryView.tsx:39](../components/LibraryView.tsx:39)).
`router.refresh()` re-renders the *server* tree; it does not re-run that client
fetch and does not remount the component. The row stays until you hit Refresh
manually.

Same path affects "Mark as watched" from the card's info modal
([MediaCard.tsx:114](../components/MediaCard.tsx:114)).

**Fix:** lift an `onChanged` callback into `LibraryView` and drop the row from
local state, the way `WatchlistSection` already does
([watchlist/page.tsx:218](../app/watchlist/page.tsx:218)). ~30 lines.

### Q2. The Search page re-queries TMDB on every keystroke

`onChange={e => { setQuery(e.target.value); search(e.target.value) }}`
([search/page.tsx:44](../app/search/page.tsx:44)) — no debounce, no
`AbortController`. Typing "breaking bad" fires 12 requests, and because
responses are applied unconditionally, a slow early response can overwrite a
fast later one and leave you looking at results for "brea".

The annoying part: `DashboardSearchBar` already solves this properly — 350 ms
debounce plus abort-on-supersede plus an `AbortError` guard
([DashboardSearchBar.tsx:52-96](../components/DashboardSearchBar.tsx:52)). The
dedicated search page is the worse of the two. Port the logic across.

### Q3. Marking something watched twice silently does nothing

`/api/watch` POST returns **409 "Already in your watch history"** when a
non-rewatch entry exists ([api/watch/route.ts:52](../app/api/watch/route.ts:52)).
No caller checks `res.ok` — `useMediaActions.markWatched` just returns the
Response ([useMediaActions.ts:25](../lib/useMediaActions.ts:25)), and
`MediaInfoModal.handleWatchedClick` wraps it in a try/catch around a call that
never throws, then optimistically sets `isWatched: true`
([MediaInfoModal.tsx:120](../components/MediaInfoModal.tsx:120)).

So the button reports success on a request that failed. Two fixes, do both:
check `res.ok` in the hook and throw, and see F1 below for what the 409 should
actually offer.

### Q4. Stats: the "episodes" line on the monthly chart isn't episodes

`computeMonthlyActivity` buckets **watch_entries**, and files anything that
isn't a movie under `episodes` ([stats.ts:41](../lib/stats.ts:41)). A show you
logged once contributes 1 "episode". Meanwhile the Episodes stat tile counts
real `episode_progress` rows ([stats/page.tsx:12](../app/stats/page.tsx:12)), so
the two numbers on the same page disagree by construction.

Fix: pass `episode_progress` (which has `watched_at`) into
`computeMonthlyActivity` and bucket it separately. The page already queries the
table — it just selects `id` and throws the dates away.

### Q5. Stats: "Hours" undercounts TV by roughly everything

`totalHours` sums `media.runtime_mins` per watch entry
([stats/page.tsx:18](../app/stats/page.tsx:18)). For shows, `runtime_mins` is
`episode_run_time[0]` — a *single episode's* length
([tmdb.ts:241](../lib/tmdb.ts:241)). So a 62-episode show you fully tracked
counts as ~45 minutes, and the 82 seasons' worth of `episode_progress` rows
contribute zero.

Fix: hours = movie runtimes + (episode_progress count × that show's
`runtime_mins`). Roughly 15 lines in `lib/stats.ts`, and it's a testable pure
function like the rest of that file.

## Tier 2 — the app never tells you anything

### Q6. There is no notification system at all

Zero matches for `toast`, `aria-live`, or `role="status"` across the codebase.
Every mutation either silently succeeds or `console.error`s to a console nobody
has open — `handleUpdatePriority`, `handleRemove`, `handleMarkAsWatched`
([watchlist/page.tsx:203,222,243](../app/watchlist/page.tsx:203)),
`handleBatchAction` ([MultiSelectProvider.tsx:86](../components/MultiSelectProvider.tsx:86)).

This is the single highest ratio of perceived-quality to effort in the list. A
~60-line context provider with a portal and an `aria-live` region, then replace
the `console.error`s. Everything else in Tier 2 gets easier once it exists.

### Q7. Destructive actions have no undo, and inconsistent confirmation

The only guard in the app is a native `confirm()` on watch-entry delete
([MediaCard.tsx:54](../components/MediaCard.tsx:54)). Removing from the
watchlist deletes instantly with no prompt
([watchlist/page.tsx:210](../app/watchlist/page.tsx:210)), and un-checking an
episode in the tracker cascades — it silently deletes *every watched episode
after it* in that season ([EpisodeTracker.tsx:29-36](../components/EpisodeTracker.tsx:29)).
Misclick E1 of a finished season and you lose the whole season with no warning.

Once Q6 lands, the better pattern is optimistic removal + a 5-second "Undo"
toast, and drop the `confirm()` entirely.

### Q8. Escape doesn't close modals; nothing is trapped or locked

No `keydown` handler exists anywhere in the app. `MediaInfoModal`,
`EditEntryModal`, and `SimilarModal` close only on backdrop click. None sets
`role="dialog"`/`aria-modal`, none traps focus, none locks body scroll — so on
mobile the page behind a modal scrolls under your finger.

Fix once as a `useModal(onClose)` hook (Escape + scroll lock + focus restore),
apply to all three. ~40 lines total.

### Q9. No keyboard shortcuts

No `/` or `⌘K` to focus search, no `j`/`k` through results. For an app whose
primary loop is "search, log, close", this is the difference between three
seconds and fifteen. Cheap once Q8's key handling exists.

## Tier 3 — features the data already supports

### F1. Rewatch logging (schema and API are done; no UI exists)

`watch_entries.rewatch` has existed since migration 001
([001_initial.sql:34](../supabase/migrations/001_initial.sql)), and
`/api/watch` POST reads and honours it
([api/watch/route.ts:40](../app/api/watch/route.ts:40)). Grep says **nothing in
the UI ever sends it.** The entire feature is one boolean away from working.

The 409 from Q3 is the natural hook: when the API says "already watched", the
modal should offer "Log a rewatch" instead of failing silently. That plus a
rewatch count on the card is a day of work at most, and it's the feature a
media tracker is most obviously missing.

### F2. Episode tracker is missing its three most-wanted affordances

[EpisodeTracker.tsx](../components/EpisodeTracker.tsx) renders numbered buttons
only. It has no:

- **"Mark whole season watched"** — currently 24 clicks, though the
  click-to-here cascade at line 22 already does the batching, so the button is
  ~10 lines against an API that already accepts arrays.
- **Episode titles or air dates** — the grid says `E1 … E24` and nothing else.
  Requires storing TMDB's per-season episode list; the `seasons` table only
  keeps `episode_count`. This is the one genuinely multi-day item here. *(Done:
  migration 008 + `/api/episodes/meta`. It came in under a day because the fill
  is lazy — no backfill script, no change to the ingest path.)*
- **Specials** — `season_number > 0` is filtered out at ingest
  ([tmdb.ts:245](../lib/tmdb.ts:245)), so season 0 is permanently untrackable.
  Deliberate-looking, but worth a decision rather than an accident.

### F3. You can't rate a show you're tracking

`/show/[id]` renders `RatingStars` only when a `watch_entries` row exists
([show/[id]/page.tsx:110](../app/show/[id]/page.tsx:110)). Tracking episodes
never creates one. So the normal path — start a show, watch episodes — leaves
you on a page with no way to rate it, and no way to mark the show watched.

Add a "Mark show as watched" button that POSTs to `/api/watch`; the stars then
appear via the existing code path.

### F4. Library search only matches titles

`entry.media?.title.toLowerCase().includes(...)`
([LibraryView.tsx:54](../components/LibraryView.tsx:54)). `director`,
`cast_members`, and `genres` are all in the row and all ignored. Searching your
own library for "Fincher" or "Pedro Pascal" returns nothing. One line to widen
the predicate, and it makes the `/person/[name]` page reachable by search
rather than only by clicking a director link.

### F5. Library has no filters; the watchlist's genre filter is hardcoded

`/movies` and `/shows` offer sort + title search, nothing else — no genre, no
year, no rating floor, no "unrated only". The watchlist does have a genre
dropdown, but it's a hand-written 26-entry array
([watchlist/page.tsx:27](../app/watchlist/page.tsx:27)) rather than the genres
actually present in the user's library, so most options return nothing. Derive
it from the data.

### F6. No signup or password reset

[login/page.tsx](../app/login/page.tsx) calls `signInWithPassword` and nothing
else. There is no signup route, no "forgot password" link, no OAuth. Fine for a
single-user app — but `PasswordChangeForm` in settings implies otherwise, and
account recovery currently means a Supabase dashboard visit. Decide which app
this is.

*(Done: invite-gated multi-user. See the status section for the three settings
it needs. One caveat worth knowing — PKCE stores its code verifier in a cookie,
so an emailed link has to be opened in the browser that requested it. Open a
reset link on your phone after asking for it on your laptop and the exchange
fails; `/auth/callback` sends that back to the login screen with the reason
rather than dropping you on a blank form.)*

### F7. Bulk actions swallow partial failure

`handleBatchAction` uses `Promise.all`
([MultiSelectProvider.tsx:59](../components/MultiSelectProvider.tsx:59)). One
409 rejects the whole thing, the `catch` logs to console, and the selection is
*not* cleared — but the items that did succeed already wrote. You get no
indication of which. Switch to `Promise.allSettled` and report counts (needs
Q6). Also missing: "select all" on the library and watchlist pages.

## Tier 4 — polish

### P1. 26 raw `<img>` tags, no `next/image` anywhere

Every poster in the app is an unoptimized full-size TMDB `w500` JPEG:
`MediaInfoModal` ×2, `PopularCollectionsFeed` ×2, `person/[name]` ×2,
`collections/[id]` ×2, and one each across 15 more files. No `width`/`height`
either, so every list reflows as posters land.

Carried over from the last audit, where I declined it as unverifiable without a
runnable app. It still needs a real browser to confirm — `next.config` needs
`images.remotePatterns` for `image.tmdb.org` and every call site needs
dimensions. Worth doing, worth doing *while looking at it*.

### P2. `/show/[id]` does four sequential round trips

media → seasons → progress → entry, each awaiting the last
([show/[id]/page.tsx:20-42](../app/show/[id]/page.tsx:20)). Only `progress`
genuinely depends on `seasons`; the other three can go in a `Promise.all`. The
page also shows a bare `Loading...` string where every other route has a
skeleton, and it queries Supabase directly from the browser rather than going
through an API route like the rest of the app.

### P3. The library loads everything, forever

`LibraryView` fetches all watch entries with full media joins in one request and
renders them all ([LibraryView.tsx:33](../components/LibraryView.tsx:33)) —
while the watchlist paginates at 24 with an IntersectionObserver. At 258 media
rows this is fine today. It is the kind of fine that stops being fine silently.

### P4. Mobile top-bar search icon is decorative

[Sidebar.tsx:861](../components/Sidebar.tsx:861) renders a `Search` icon in the
mobile header with no link and no handler. It looks tappable and does nothing.

## What still needs a browser

The four completed items are covered by 19 new tests, but tests do not catch
everything. Worth five minutes each when you next have the app running:

- **Toast placement.** Bottom-right on desktop, bottom-centre on mobile, at
  `z-[110]`. It is meant to clear both the mobile bottom nav and the
  multi-select action bar at `z-[100]`. Those offsets were reasoned about, not
  seen. Select two items and delete a third to put both bars on screen at once.
- **The rewatch loop.** Open something already in your history and press
  **Log rewatch** — it should insert a second row rather than 409. Then mark
  something unwatched twice: the second press should offer the rewatch in a
  toast rather than silently doing nothing.
- **Deleting from `/movies`.** The row should vanish immediately (Q1). This is
  tested, but the test mocks `fetch`.
- **The whole auth loop (F6).** Sign out, ask for a reset, follow the emailed
  link, set a password, sign in with it. Then create an account with the invite
  code, and again with a wrong one. Six of the eight steps involve an email
  Supabase sends and a redirect allow-list only you can configure, so none of it
  is reachable from tests.
- **The first load of a show page (F2).** This is the only change in either
  round that writes rows the app has never written before. Open a show, wait a
  beat, reload: the numbers should become titles, and stay titles. If they do
  not, `select count(*) from episodes` says whether the fill wrote anything or
  the request failed. A long show pays one TMDB request per season on that
  first load only.

## Corrections to this document

- **Q5 was only half the story.** Fixing the arithmetic made the number *worse*
  in practice — 405 hours to 402 — because 24 of the 26 shows in the live
  database have a null `runtime_mins`. The mapping read only TMDB's
  `episode_run_time`, a field TMDB has been deprecating and now returns empty
  for most shows. Verified directly against the database rather than assumed.
  The real total is roughly 133 hours higher than either number. Fixed at the
  source, but existing rows need the backfill named at the top of this doc.
- **Q7 landed as deferred execution, not undo-after-the-fact.** Delete-then-
  restore cannot rebuild a watch entry faithfully: `POST /api/watch` refuses a
  duplicate unless `rewatch` is set, so the restored row would come back with
  that flag flipped. Deferring the write for six seconds means Undo cancels
  something that has not happened yet. Trade-off: a hard tab close inside the
  window loses the delete, which fails safe.
- **The `confirm()` on library delete is gone**, replaced by the undo. Q7 called
  for consistent confirmation; consistent *undo* turned out to be the better
  answer, since it costs nothing on the common path.

- ~~**Q7 partially overtaken.** The episode-tracker cascade delete is unchanged,
  but destructive watchlist and library actions now at least report what they
  did. Undo still does not exist.~~ Written after round one; the cascade and
  both destructive actions now have undo, per the correction above.
- **Q4/Q5 unchanged but now cheaper.** Both are pure functions in `lib/stats.ts`
  with an existing test file, so they are still the best hour-or-less items.
